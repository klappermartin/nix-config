# Fix runtime contracts, preserve sound architecture

## Executive verdict

**Your configuration is structurally sound and appropriately modular for one Apple Silicon Mac; its most important weaknesses are in runtime service ownership and custom-script behavior.** The locked `mb-pro` system evaluated successfully, with no Darwin or Home Manager warnings and no failed assertions. Nevertheless, live inspection found the managed skhd service failing against another running instance, and isolated behavioral checks reproduced unsafe orphan classification in the automatic reference pruner, a broken Git branch-exclusion filter, and a Sketchybar callback exception. These findings justify targeted repairs before organizational refactoring. The Homebrew setup is carefully integrated, but its documentation understates cleanup scope and overstates reproducibility. Compared with four concrete public configurations, your explicit imports, shared package set, and narrow overrides are already idiomatic; a framework migration would not address the demonstrated failures. **Successful evaluation is not runtime validation: no package build, full rebuild, or activation was performed, and this review establishes no causal connection between Nix and the reported device crash.** ([Evaluation record](../research_notes/Nix%20darwin%20configuration%20review/system.md#validation-transcript), [runtime evidence](../research_notes/Nix%20darwin%20configuration%20review/runtime.md), [comparison evidence](../research_notes/Nix%20darwin%20configuration%20review/comparison.md))

This report synthesizes the three research notes collected on **25 October 2026**. Local citations identify the inspected checkout using exact `file:line` references; deployed files and upstream sources are labeled separately. **Observed** means inspected live state; **reproduced** means an isolated test exercised the relevant behavior; **inferred** means the consequence follows from source analysis but was not exercised end to end. Confidence concerns the finding itself, not whether its triggering situation has already occurred. Evaluation covers the current checkout and lock; live observations cover particular deployed processes and files. The notes do not establish that the entire running generation is identical to the evaluated checkout.

## The architecture already has the right boundaries

The root flake defines eight direct inputs, one username, and one Darwin output, `mb-pro`. Its six explicit module entries connect four local system modules with the upstream nix-homebrew and Home Manager integrations. Home Manager then separates packages, programs, and services. This makes ownership discoverable without a constructor framework or directory-scanning convention. The following map describes the actual composition, not a proposed replacement. ([`flake.nix:4–36,47–64`](../flake.nix#L4), [`darwin/home/home.nix:1–6`](../darwin/home/home.nix#L1))

```text
flake.nix / flake.lock
└── darwinConfigurations.mb-pro
    ├── darwin/system/configuration.nix
    │   └── platform, user, Nix policy, system services, macOS defaults
    ├── darwin/system/overlays.nix
    │   └── NUR + oxker from a separate, narrowly scoped nixpkgs input
    ├── nix-homebrew upstream module
    ├── darwin/system/homebrew.nix
    │   └── Homebrew installation/taps + explicit package/activation policy
    ├── Home Manager upstream Darwin module
    └── darwin/system/home-manager.nix
        └── darwin/home/home.nix
            ├── packages.nix
            ├── programs/default.nix → named program modules
            └── services/default.nix → named user-service modules
                └── Sketchybar deployment → modular Lua configuration
```

**The main package universe is shared.** Darwin, Home Manager, and NUR follow the primary nixpkgs input; `useGlobalPkgs = true` makes Home Manager consume the system package set and overlays, while `useUserPackages = true` integrates user packages into the system-managed profile. The separate `release-25.11` source supplies only `oxker` through an architecture-aware overlay. That is an isolated compatibility workaround, not an accidental whole-system stable/unstable mismatch. NUR is actually consumed by Firefox extensions. ([`flake.nix:6–21`](../flake.nix#L6), [`darwin/system/home-manager.nix:13–15`](../darwin/system/home-manager.nix#L13), [`darwin/system/overlays.nix:3–10`](../darwin/system/overlays.nix#L3), [`darwin/home/programs/firefox.nix:223`](../darwin/home/programs/firefox.nix#L223))

The platform and identity are coherent: `aarch64-darwin`, primary user `martin`, and evaluated home `/Users/martin`. **No NixOS-style hardware configuration is missing or expected.** Darwin `system.stateVersion = 5` and Home Manager `home.stateVersion = "25.05"` preserve compatibility defaults; they are not package-release selectors or evidence of stale dependencies. Home Manager explicitly selects copied applications despite its older state version. Preserve these values unless deliberately migrating affected behavior. ([`darwin/system/configuration.nix:31,206–211`](../darwin/system/configuration.nix#L31), [`darwin/home/home.nix:8–13`](../darwin/home/home.nix#L8), [Home Manager upgrade guidance](https://github.com/nix-community/home-manager/blob/master/docs/manual/usage/upgrading.md), [Darwin setup](https://github.com/nix-darwin/nix-darwin/blob/master/README.md))

### Existing strengths are worth preserving

Homebrew ownership is well defined: nix-homebrew controls installation and immutable tap sources; nix-darwin controls package declarations and activation. Deriving `homebrew.taps` from `config.nix-homebrew.taps` avoids competing lists. The locked nix-homebrew wrapper already disables automatic tap updates and the API installation path where required, so there is no demonstrated “pinned taps are ignored” defect. Global checksum enforcement with a named exception helper makes policy exceptions visible. ([`darwin/system/homebrew.nix:8–17,28–57`](../darwin/system/homebrew.nix#L8), [locked wrapper, lines 126–131](https://github.com/zhaofengli-wip/nix-homebrew/blob/c11cccfdd36dd69b5323d70d354b2853379c2426/modules/default.nix#L126-L131))

Application integration is similarly deliberate: Dock entries derive their paths from Home Manager's actual home and copied-app directory, rather than independently hard-coding a destination. The package list and program modules supply the referenced applications. SSH intentionally uses Apple's client and Keychain integration, while the signing agent invokes an absolute system executable. Home Manager's conflict-backup script names its dependencies and rotates two backup generations; `nh` also provides generation retention. These facilities are useful, although neither is a general backup of mutable application data. ([`darwin/system/configuration.nix:38–52,148`](../darwin/system/configuration.nix#L38), [`darwin/home/home.nix:11`](../darwin/home/home.nix#L11), [`darwin/home/programs/ssh.nix:3`](../darwin/home/programs/ssh.nix#L3), [`darwin/home/programs/git.nix:126`](../darwin/home/programs/git.nix#L126), [`darwin/system/home-manager.nix:16`](../darwin/system/home-manager.nix#L16))

Reusable feature modules already exist: `programs.oss-references` exposes typed configuration, and its pruner has its own options and a dependency assertion. Its module design is useful even though its deletion algorithm needs repair. OpenCode packaging also has clear boundaries: hashed platform assets, an explicit Node executable, a fail-loud Codegraph patch, disabled V2 self-update, and separate V1/V2 execution paths. Mutable runtime plugins and selected profiles remain outside those guarantees. Existing legacy configuration fields alone are not a demonstrated migration defect under the documented V2 compatibility contract. ([`darwin/home/programs/oss-references.nix:9–33`](../darwin/home/programs/oss-references.nix#L9), [`darwin/home/services/oss-references-pruner.nix:27`](../darwin/home/services/oss-references-pruner.nix#L27), [`darwin/home/programs/opencode/default.nix:13–138`](../darwin/home/programs/opencode/default.nix#L13), [OpenCode migration contract](https://opencode.ai/v2/docs/migrate-v1))

## Fix destructive selection and service ownership first

Priorities reflect both consequences and evidence: **P1** warrants the next repair session, **P2** belongs in the next maintenance pass, and **P3** is conditional hardening or cleanup. An isolated reproduction establishes a defect without establishing that it has already damaged user state.

### P1 — Automatic reference pruning can classify a used clone as orphaned

**High confidence; reproduced classification defects, no observed deletion.** The scan silently skips missing consumer roots and suppresses discovery errors. It protects only an exact resolved target matching the clone directory, so a consumer symlink to a file or subdirectory does not protect its parent clone. In-memory fixtures exercising the actual `cmd_prune --dry-run` function classified a candidate as orphaned both when a descendant target existed and when consumer discovery failed. The configured weekly agent invokes destructive mode with `--yes --min-age 7d`; directory mtime measures neither last use nor continued reads. ([`darwin/home/programs/oss-ref.sh:194–248`](../darwin/home/programs/oss-ref.sh#L194), [`darwin/home/services/oss-references-pruner.nix:42`](../darwin/home/services/oss-references-pruner.nix#L42), [reproduction record, R3](../research_notes/Nix%20darwin%20configuration%20review/runtime.md))

The operational triggers are concrete: an unavailable or unreadable consumer tree, a link into a clone rather than to its root, or a consumer outside the configured search roots. The last case is permitted by `add`, which accepts an arbitrary destination without registering it or checking its inclusion in discovery scope. Actual prevalence depends on your directory layout; **the review found unsafe eligibility logic, not evidence of lost data**. ([`darwin/home/programs/oss-ref.sh:92,202–223`](../darwin/home/programs/oss-ref.sh#L92), [`darwin/home/programs/oss-references.nix:33`](../darwin/home/programs/oss-references.nix#L33))

**Recommended action:** suspend destructive scheduled pruning or make it reporting-only until discovery failures abort deletion, descendant targets protect the containing managed clone, and consumer scope is enforced or explicitly registered. Acceptance should include disposable-directory fixtures covering missing/unreadable roots, descendant links, outside-scope consumers, retained used clones, and genuinely unused eligible clones. Preserve dry-run output and make incomplete scans visible. These are proposed repairs and checks; none was applied.

### P1 — Two skhd owners compete, and the declarative service lacks its execution environment

**High confidence; live service failure observed.** Home Manager enables `org.nix-community.home.skhd`, but the separately installed `com.koekeishiya.skhd` was running during inspection. The managed service reported `state = spawn scheduled` and exit code 1; its log repeatedly reported `could not lock pid-file! abort..`. The reviewed upstream implementation uses a per-user PID lock, explaining the conflict. Home Manager's `KeepAlive` setting repeatedly retries. The large accumulated error log is historical evidence, not a measured failure rate or proof of crash causation. ([`darwin/home/services/skhd.nix:34–36`](../darwin/home/services/skhd.nix#L34), [competing deployed plist, lines 5–11](file:///Users/martin/Library/LaunchAgents/com.koekeishiya.skhd.plist#L5), [deployed managed log](file:///Users/martin/Library/Logs/skhd/skhd.err.log), [skhd PID-lock implementation](https://github.com/koekeishiya/skhd/blob/v0.3.9/src/skhd.c), [live inspection record, R1](../research_notes/Nix%20darwin%20configuration%20review/runtime.md))

**A second, independently reproduced defect remains after ownership is fixed.** The managed service has the ordinary launchd PATH `/usr/bin:/bin:/usr/sbin:/sbin` and no observed `SHELL`. Under that PATH, `yabai`, `sketchybar`, and `skhd` were unavailable; `/usr/bin/jq` was available on this machine. Meanwhile, generated space commands use zsh-specific `$SPACES[1]` indexing. Upstream skhd falls back to `/bin/bash` when `SHELL` is absent. A stubbed test of the exact expression passed `11[1]` under Bash and the intended `11` under zsh. The running competing agent's broader mutable PATH does not make the declarative service self-contained. ([`darwin/home/services/skhd.nix:7–15,34–44`](../darwin/home/services/skhd.nix#L7), [locked Home Manager service module](https://github.com/nix-community/home-manager/blob/2cd3234928f60bbff695a7ee56115ef7799c47cd/modules/services/skhd.nix#L61-L70), [upstream shell selection](https://github.com/koekeishiya/skhd/blob/v0.3.9/src/hotkey.c), [environment and parsing checks, R2](../research_notes/Nix%20darwin%20configuration%20review/runtime.md))

**Recommended action:** deliberately choose one service owner, then give the managed service an explicit zsh interpreter and declared command dependencies, or move the actions into packaged scripts with explicit interpreters. Fixing executable paths alone does not repair the shell syntax. After an authorized activation, verify one running owner, no new PID-lock failures, and actual space/window hotkeys. Accessibility permissions and Yabai's installed-version capabilities still need runtime checks; disabling its scripting addition alone is insufficient evidence that all space-focus commands are broken.

### P2 — `git sweep` fails to exclude the default branch

**High confidence; filter failure reproduced without deleting branches.** The alias uses `grep -E -v ' $(git defaultBranch)$'`. Single quotes prevent command substitution, and the resulting expression does not exclude ordinary default-branch names. A fixture containing `main`, the current feature branch, and another merged branch passed all lines through unchanged. Consequently, a deletable default branch can reach `git branch -d`; the current-branch marker also reaches `xargs`, creating errors that can prevent the trailing remote-prune command. This concerns local branch references, not demonstrated loss of committed objects. ([`darwin/home/programs/git.nix:42–45`](../darwin/home/programs/git.nix#L42), [filter reproduction, R4](../research_notes/Nix%20darwin%20configuration%20review/runtime.md))

**Recommended action:** enumerate plain branch names with `for-each-ref`, explicitly exclude the current and default branches, and pass arguments robustly. Also replace `cut -d'/' -f4` in `defaultBranch`: it truncates `origin/release/stable` to `release`, affecting both `sweep` and `m`. Validate in a disposable repository with a slash-containing default branch before relying on the alias. ([`darwin/home/programs/git.nix:42,55`](../darwin/home/programs/git.nix#L42))

### P2 — Sketchybar's network metric can throw and reverses traffic directions

**High confidence; callback exception reproduced with the configured Lua version.** Counter deltas are divided by two, producing fractional rates for odd deltas; the below-1000 formatter passes those values to `%d`. Lua 5.5 rejects a nonintegral number there. The actual Lua module, loaded with an in-memory `sbar` stub, failed on a one-byte delta with `number has no integer representation`. The proven impact is a failed callback and missing label update, not a demonstrated crash of the whole bar. Round the low-rate value or use a floating-point format. ([`darwin/home/sketchybar/items/network.lua:9–11,43–50`](../darwin/home/sketchybar/items/network.lua#L9), [callback reproduction, R7](../research_notes/Nix%20darwin%20configuration%20review/runtime.md))

**High confidence; direction mismatch confirmed against local command output.** The code labels `netstat -ibn` columns 7 and 10 as TX and RX, respectively; the inspected Darwin header identifies those columns as inbound and outbound bytes. Correct the assignment or display order. Separately, hard-coded `en0` and a fixed two-second divisor create inferred inaccuracies after interface changes, delayed callbacks, or hidden-bar pauses. Parameterize the intended interface and measure elapsed time when improving the metric. The deployed Lua interpreter and C module both use Lua 5.5, so an ABI mismatch is not the supported explanation. ([`darwin/home/sketchybar/items/network.lua:36–58`](../darwin/home/sketchybar/items/network.lua#L36), [`darwin/home/sketchybar/items/wifi.lua:22`](../darwin/home/sketchybar/items/wifi.lua#L22), [`darwin/home/sketchybar/default.lua:5`](../darwin/home/sketchybar/default.lua#L5), [live ABI and direction evidence](../research_notes/Nix%20darwin%20configuration%20review/runtime.md))

### P2/P3 — Smaller script and dependency defects merit focused follow-up

**OSS add: high confidence from source; failure scenarios not exercised against real repositories.** Failed clone commands capture stderr into a temporary file that is subsequently removed without printing it. Existing clone targets are always rejected, preventing normal same-version reuse. The script publishes the clone before creating the consumer link, so a linking failure leaves a target that a retry then refuses. An existing real-directory destination also invokes `ln`'s directory semantics rather than the advertised simple link replacement. Surface clone diagnostics, validate destination type, support verified reuse, and report partial success accurately. ([`darwin/home/programs/oss-ref.sh:103–142`](../darwin/home/programs/oss-ref.sh#L103))

**Profile switching: medium confidence operational risk, inferred from filesystem sequencing.** The OMO switcher uses a fixed `.omo.jsonc.tmp` name without cleanup; interruption can leave it behind, and concurrent invocations compete for it. Its default branch removes the active selection before copying the replacement. A unique sibling temporary path, cleanup trap, and atomic final rename would improve recovery. No profile switch or concurrency incident was observed. The documented mutable default-profile behavior itself is intentional. ([`darwin/home/programs/opencode/activate-oh-my-openagent-profile.sh:28–46`](../darwin/home/programs/opencode/activate-oh-my-openagent-profile.sh#L28), [`darwin/home/programs/opencode/README.md:70`](../darwin/home/programs/opencode/README.md#L70))

**`pn` dependency: high confidence declaration gap, environment-scoped availability result.** Zsh aliases `pn` to `pnpm`, but the reviewed global package/module declarations do not supply pnpm, and it was absent from the review process's PATH. Declare it if this alias is intended to work globally; otherwise document that a project environment must supply it. This does not establish failure in a project using direnv/devenv. ([`darwin/home/programs/zsh.nix:96–99`](../darwin/home/programs/zsh.nix#L96), [`darwin/home/packages.nix:6`](../darwin/home/packages.nix#L6), [`darwin/home/programs/default.nix:57`](../darwin/home/programs/default.nix#L57))

## Clarify policy, then improve only genuine extension points

### Homebrew cleanup and update guarantees need precise wording

**P2; high-confidence documentation mismatch.** The local comment and README describe `cleanup = "zap"` as removing casks dropped from this list. The locked nix-darwin implementation defines cleanup over installed Homebrew packages absent from the generated Brewfile, including independently installed packages; cask zap rules can additionally remove associated state. This may be your intended exclusive-ownership policy, but the narrower wording can mislead a future manual installation. No actual deletion or affected-package inventory was observed. State the full scope, and retain `zap` only if Homebrew is intended to be exclusively declarative. `uninstall` still removes unlisted packages; it merely avoids the additional cask zap behavior. ([`darwin/system/homebrew.nix:36–37`](../darwin/system/homebrew.nix#L36), [`README.md:80–83`](../README.md#L80), [locked cleanup semantics, lines 79–110](https://github.com/nix-darwin/nix-darwin/blob/bb0b90dbd54e207100de72b5dcbe3188c98a4b69/modules/homebrew.nix#L79-L110))

**P2; high-confidence reproducibility overstatement.** The claim that upgrades occur only after `nix flake update` is too strong. All seven evaluated casks are greedy, and four waive checksum enforcement. A pinned recipe can still refer to mutable vendor bytes, and application self-updaters are a separate channel. The inspected installed Spotify recipe corroborated this with an unversioned URL, `sha256 :no_check`, and `auto_updates true`, although its identity against the checkout's pinned tap revision was not proven. The defensible contract is: **tap recipes are lock-pinned; unchecked downloads and app-managed updates can change independently**. Nix generation rollback should not be described as restoring all Homebrew versions or zapped application data. ([`darwin/system/homebrew.nix:40–63`](../darwin/system/homebrew.nix#L40), [locked greedy semantics](https://github.com/nix-darwin/nix-darwin/blob/bb0b90dbd54e207100de72b5dcbe3188c98a4b69/modules/homebrew.nix#L601-L607), [installed Spotify recipe, lines 4–17](file:///opt/homebrew/Library/Taps/homebrew/homebrew-cask/Casks/s/spotify.rb#L4))

### Bootstrap and maintenance need an explicit target and staged verification

**P2; confirmed portability gap, not a reproduced failure on this Mac.** README commands use `--flake .`, while the only output is `mb-pro`; darwin-rebuild defaults an omitted selector from `LocalHostName`. Document `--flake .#mb-pro` so fresh-machine instructions do not depend on matching hostnames. The initial bootstrap command also fetches darwin-rebuild from moving `master`, whereas the configuration uses a locked input; explain that choice or deliberately align the bootstrap tool with the chosen input. Document username/platform customization, Xcode's manual prerequisite, required macOS permissions, and recovery boundaries. ([`README.md:39–49`](../README.md#L39), [`flake.nix:51–64`](../flake.nix#L51), [`darwin/system/configuration.nix:8`](../darwin/system/configuration.nix#L8), [locked hostname selection](https://github.com/nix-darwin/nix-darwin/blob/bb0b90dbd54e207100de72b5dcbe3188c98a4b69/pkgs/nix-tools/darwin-rebuild.sh#L162-L172))

The flake exposes a formatter but no `checks` output. Integrated Home Manager does not require a standalone `homeConfigurations` output, and its absence is not a defect. A small explicit Darwin evaluation target is the useful missing operational affordance: generic `nix flake check` does not automatically establish that this nonstandard Darwin output was forced or built. ([`flake.nix:38–64`](../flake.nix#L38), [recognized flake-check outputs](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake-check.html))

### Extensibility should follow actual variation

The 212-line system module mixes base Nix policy, authentication, system services/window management, defaults, and identity. Optional extraction of `defaults.nix` and a service/window-management module would improve navigation while preserving explicit imports. A development/desktop split of the plain package list is also reasonable if it improves maintenance; a module per package is unnecessary. Keep the oxker pin centralized and attach a retest/removal condition when revisiting it. The localized PrismLauncher override already documents its rationale and is a good pattern to retain. ([`darwin/system/configuration.nix:8–211`](../darwin/system/configuration.nix#L8), [`README.md:99`](../README.md#L99), [`darwin/system/overlays.nix:5`](../darwin/system/overlays.nix#L5), [`darwin/home/packages.nix:42`](../darwin/home/packages.nix#L42))

More valuable shared settings lie at runtime boundaries: skhd models four spaces per display while Sketchybar renders ten space items; network widgets repeat `en0`; Sketchybar reconstructs `/Users/$USER` and deploys to literal configuration directories. Centralize these only where you want them configurable, using the existing home/XDG options and a shared intended space model. They are portability and consistency limitations, not proof that the current layout is broken. The ff2mpv launcher likewise works through the current per-user profile layout, but referencing the configured mpv package directly would express its dependency more robustly. ([`darwin/home/services/skhd.nix:7`](../darwin/home/services/skhd.nix#L7), [`darwin/home/sketchybar/items/spaces.lua:7`](../darwin/home/sketchybar/items/spaces.lua#L7), [`darwin/home/sketchybar/helpers/init.lua:2`](../darwin/home/sketchybar/helpers/init.lua#L2), [`darwin/home/services/sketchybar.nix:6`](../darwin/home/services/sketchybar.nix#L6), [`darwin/home/programs/mpv.nix:15–18`](../darwin/home/programs/mpv.nix#L15))

Small housekeeping can wait: JetBrains Mono is declared directly and through Kitty, which is redundant but does not double store contents; the README's btop path omits its actual directory prefix. Firefox preference-type candidates and overlapping VSCodium Python choices were not checked against application-version semantics and should remain follow-up questions rather than confirmed failures. ([`darwin/home/packages.nix:31`](../darwin/home/packages.nix#L31), [`darwin/home/programs/kitty.nix:14–16`](../darwin/home/programs/kitty.nix#L14), [`README.md:135–136`](../README.md#L135), [`darwin/home/programs/firefox.nix:37`](../darwin/home/programs/firefox.nix#L37), [`darwin/home/programs/vscodium.nix:269`](../darwin/home/programs/vscodium.nix#L269))

These are four source-inspected snapshots, not a statistical survey or a guarantee that the public systems build. Their value is concrete comparison: experienced users make different tradeoffs, and their abstractions usually reflect additional hosts, platforms, or roles.

| Public configuration | Observed pattern | Appropriate lesson for this Mac |

For a second Mac, a narrow `hosts/mb-pro/default.nix` composition/identity layer would become useful. For Linux, extract genuinely portable home configuration while retaining Darwin-specific services and applications. Until those requirements exist, explicit imports and the current module hierarchy are easier to audit. Neither flake-parts, automatic imports, a universal host factory, nor enable flags around every individual program would repair the issues established here.

## Conclusion

The meaningful next step is to make the declared environment match the environment that actually executes: one service owner, explicit shell dependencies, reliable consumer discovery, and accurate boundaries around mutable applications. Those contracts determine whether this Mac behaves reproducibly far more directly than an additional directory hierarchy would.

The configuration already provides a credible foundation for growth. Repairing the demonstrated runtime logic and adopting a small, staged verification routine will improve reliability while keeping the system understandable to its single owner.
