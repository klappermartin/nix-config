# Experienced-user nix-darwin / Home Manager practices compared with `/Users/martin/nix`

Research date: 2026-10-25. Scope: architecture and operating practices, based on source inspection; no evaluations, builds, activation, configuration edits, or additional agents. Local links refer to inspected files in this checkout. Public examples are comparative evidence, not endorsements of every setting. Repository snapshots are pinned below so later changes do not obscure the evidence.

## 1. What do credible public configurations actually do, and which architecture fits this repository?

### Takeaway

The existing single-host configuration is already idiomatic: a small flake, explicit module composition, separate Darwin and Home Manager layers, shared `pkgs`, and a centralized username. Experienced configurations differ substantially in abstraction and import style; their extra layers generally solve multi-host/platform problems that this checkout does not yet have. [Local flake](file:///Users/martin/nix/flake.nix) · [Official Home Manager Darwin example](https://github.com/nix-community/home-manager/blob/master/docs/manual/nix-flakes/nix-darwin.md)

### Cited Findings

#### Local architecture and strengths

- `flake.nix:47–63` defines one user (`martin`), one host (`mb-pro`), and an explicit six-entry module list: system configuration, overlays, nix-homebrew module, Homebrew configuration, Home Manager module, and Home Manager wiring. This makes the composition directly discoverable without a host-construction framework. [Source](file:///Users/martin/nix/flake.nix)
- The Home Manager bridge uses both `useGlobalPkgs = true` and `useUserPackages = true`, passes `inputs` through `extraSpecialArgs`, and imports `../home/home.nix`. This closely matches the official integration example. The shared package set also makes system overlays available to HM consumers. [Local bridge](file:///Users/martin/nix/darwin/system/home-manager.nix) · [Official example](https://github.com/nix-community/home-manager/blob/master/docs/manual/nix-flakes/nix-darwin.md)
- Home Manager has an explicit three-way split into packages, programs, and services. Programs and services have explicit `default.nix` import lists. The system sets `nixpkgs.hostPlatform = "aarch64-darwin"`, `system.primaryUser`, and the user home directory. These are meaningful boundaries for a single Mac/user; a `hosts/` directory is not needed to make them valid. [Home](file:///Users/martin/nix/darwin/home/home.nix) · [Programs](file:///Users/martin/nix/darwin/home/programs/default.nix) · [Services](file:///Users/martin/nix/darwin/home/services/default.nix) · [System](file:///Users/martin/nix/darwin/system/configuration.nix)
- This repository already uses reusable module options where they have a purpose: `programs.oss-references` exposes typed enable/package/root/consumerRoots options and gates implementation with `mkIf`; its pruning service exposes options, gates Darwin behavior, and asserts that the base feature is enabled. It would be inaccurate to describe the repository as lacking feature modules. [Program module](file:///Users/martin/nix/darwin/home/programs/oss-references.nix) · [Service module](file:///Users/martin/nix/darwin/home/services/oss-references-pruner.nix)

### Inferences

- **Keep explicit imports for this repository.** They make enabled modules visible in review; adding a file does not silently activate it. Automatic import discovery saves repetitive lists in large trees but makes naming/layout part of activation semantics. Both styles are demonstrated above; the choice is maintainability preference, not a Nix requirement.
- **Extract only real variations.** A second Mac warrants a small host module for hostname/platform/machine-specific settings, while retaining shared Darwin and home modules. A second user warrants a user boundary. A reusable bundle spanning packages/config/services warrants typed options. No evidence here warrants adding flake-parts, a registry, a universal `mkHost`, or enable flags around every one-off program today.
- **No missing Darwin hardware configuration.** The official Darwin setup requires a host platform and configuration modules; it does not introduce NixOS's generated disk/kernel hardware configuration workflow. The current platform declaration is the relevant baseline. [Official setup](https://github.com/nix-darwin/nix-darwin/blob/master/README.md)

### Gaps

- This is a purposive four-repository comparison, not a statistical survey of experienced users. No claim of universal consensus is justified.
- Code reading establishes patterns, not that every public configuration currently builds or is suitable to copy. The repositories contain personal assumptions and operational choices.

## 2. Which compatibility and reproducibility practices are requirements, and which are preferences?

### Takeaway

The main input families are aligned with the official unstable setup; the stable input is a scoped package workaround, not evidence of a mismatched system. Preserve stateVersion unless deliberately migrating behavior. Immutable Homebrew taps improve control, but they do not give every cask Nix-store immutability or rollback semantics. [Local inputs](file:///Users/martin/nix/flake.nix) · [Local overlay](file:///Users/martin/nix/darwin/system/overlays.nix) · [HM upgrade guide](https://github.com/nix-community/home-manager/blob/master/docs/manual/usage/upgrading.md) · [nix-homebrew scope](https://github.com/zhaofengli/nix-homebrew/blob/main/README.md)

### Cited Findings

- **Supported compatibility policy:** official nix-darwin documentation pairs `nixpkgs-unstable` with Darwin `master` and uses `follows = "nixpkgs"`; HM documents `master` for unstable and matching release branches for stable. Local Darwin, HM, and NUR follow the primary unstable nixpkgs input. This is the expected branch family; `follows` shares a dependency, but does not prove any particular newly updated revisions build together. [Darwin README](https://github.com/nix-darwin/nix-darwin/blob/master/README.md) · [HM guide](https://github.com/nix-community/home-manager/blob/master/docs/manual/usage/upgrading.md) · [Local flake](file:///Users/martin/nix/flake.nix)
- **Scoped secondary package sets are normal:** local `nixpkgs-stable-2511` supplies only `oxker` through an overlay, with an upstream regression explanation. Mitchell similarly uses a stable primary nixpkgs plus unstable package substitutions and an older specific input; Ryan carries several targeted package sources with removal conditions. These are package-selection techniques, not reasons to change HM's branch to match the secondary source. [Local overlay](file:///Users/martin/nix/darwin/system/overlays.nix) · [Mitchell flake](https://github.com/mitchellh/nixos-config/blob/40d483d74cf48d64379fc9a857237ee18c519ff4/flake.nix) · [Ryan flake](https://github.com/ryan4yin/nix-config/blob/b334336cd9e4970c8e35a6cb154a57f4051ba77a/flake.nix)
- **State compatibility is distinct from package freshness:** local Darwin stateVersion is `5`, and HM stateVersion is `"25.05"`. HM explicitly says to keep the initial version when upgrading inputs and change it only after reviewing release notes and migrating affected configuration. Darwin's option definition likewise describes compatibility defaults for stateful data, rather than a current-release selector. [Local system](file:///Users/martin/nix/darwin/system/configuration.nix) · [Local home](file:///Users/martin/nix/darwin/home/home.nix) · [HM official guidance](https://github.com/nix-community/home-manager/blob/master/docs/manual/usage/upgrading.md) · [Darwin option source](https://github.com/nix-darwin/nix-darwin/blob/master/modules/system/version.nix)
- **Homebrew ownership is already well delineated:** nix-homebrew manages the Homebrew installation and taps; nix-darwin's `homebrew.*` manages installed packages. Local configuration pins core/cask inputs, disables mutable taps, derives `homebrew.taps` from those declarations, disables activation auto-update, enables upgrades, and uses SHA-required casks with explicit exceptions. This follows the upstream integration recipe closely. [Local Homebrew](file:///Users/martin/nix/darwin/system/homebrew.nix) · [nix-homebrew README](https://github.com/zhaofengli/nix-homebrew/blob/main/README.md)
- **Reproducibility limit:** Homebrew supports `sha256 :no_check` for upstream URLs whose contents change, and `version :latest` requires `:no_check`. Therefore locking a tap definition does not always lock downloaded bytes. Local unverified cask exceptions and greedy upgrades mean the comment that upgrades happen only after `nix flake update` is too absolute as a general guarantee. This is an inference from the settings and documented cask behavior; individual locked cask recipes were not audited here. [Homebrew cookbook](https://docs.brew.sh/Cask-Cookbook#stanza-sha256) · [Local cask helper and comment](file:///Users/martin/nix/darwin/system/homebrew.nix)
- **Cleanup is an ownership policy:** nix-darwin maps `cleanup = "zap"` to `brew bundle --zap --force-cleanup`. Local README deliberately places apps with valuable local state in nixpkgs and explains cask data removal. This is explicit and coherent, but choosing `zap` rather than `uninstall`/no cleanup is a user preference with consequences, not an experienced-user requirement. [Darwin implementation](https://github.com/nix-darwin/nix-darwin/blob/master/modules/homebrew.nix) · [Local ownership documentation](file:///Users/martin/nix/README.md)
- **Declarative versus mutable state is already documented:** local README explains that btop's persistent settings live in Nix, Herdr merges declared values into writable settings, SSH allows unmanaged local include files, and an external Reviewr plugin is installed separately with a version tag. These are useful documented boundaries, not evidence that every user preference must become immutable. [README usage notes](file:///Users/martin/nix/README.md) · [Program settings](file:///Users/martin/nix/darwin/home/programs/default.nix)

### Inferences

- **Requirements for the intended setup:** use valid module options and a correct platform; keep the primary module/package families compatible; preserve state compatibility unless intentionally migrating; respect which manager owns each installed artifact/configuration. A successful build/activation still needs verification outside this research task.
- **Strong operating practices:** commit/review lockfile updates; keep package workarounds narrow and documented; maintain a clear app ownership/update matrix; avoid accidentally installing the same application through two managers. The research did not find or claim a duplicate local installation.
- **Preferences:** stable versus unstable primary packages, one file versus several explicit modules, hostname versus platform output names, Homebrew versus Nix for individual GUI apps, custom option namespaces, automatic imports, and CI sophistication. None alone is a quality verdict.
- Keep both current stateVersion values; add a short explanation if future maintainers could mistake them for upgrade targets. Retire the oxker fallback only after confirming the original failure is resolved, not merely because its branch name looks old.
- Refine the Homebrew comment/documentation to promise pinned *tap definitions*, with exceptions for unverified/mutable downloads and app-managed updates. A system generation rollback should not be presented as restoring Homebrew app data or all external application state.

### Gaps

- The locked revisions, individual cask recipe bodies, installed app versions, and runtime state were not evaluated. This section is about declared policy and source-supported limits, not a clean-build certificate or concrete cask failure report.
- Secondary package support lifecycle and the present oxker regression status need targeted checking by the implementation/bug-review workstream before changing the fallback.

## 3. What incremental maintenance roadmap is justified?

### Takeaway

The best next improvement is a documented, repeatable update/build/activation workflow, followed by small demand-driven module extractions. Existing public configurations provide concrete examples of explicit Darwin build checks and reviewed lock updates; simply having CI files or running `nix flake check` does not establish Darwin runtime coverage. [Mitchell Makefile](https://github.com/mitchellh/nixos-config/blob/40d483d74cf48d64379fc9a857237ee18c519ff4/Makefile) · [Nix flake-check manual](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake-check.html)

### Cited Findings

- Local README documents bootstrap and direct `darwin-rebuild switch --flake .`, and the flake exposes a formatter. The inspected flake does not define `checks`, and the README has no dedicated update/build-before-switch/rollback procedure. This is a documentation/output observation, not a claim that the owner never tests or that no auxiliary script exists elsewhere. [README](file:///Users/martin/nix/README.md) · [Flake](file:///Users/martin/nix/flake.nix)
- Mitchell's `check` target combines `nix flake check --all-systems --no-build` with explicit `.config.system.build.toplevel.drvPath` evaluations for every NixOS and Darwin host. His Darwin switch target first builds `.#darwinConfigurations.${NIXNAME}.system`, then uses the built rebuild executable. This is a directly transferable small operational pattern. [Makefile](https://github.com/mitchellh/nixos-config/blob/40d483d74cf48d64379fc9a857237ee18c519ff4/Makefile)
- Nix's flake-check documentation lists recognized outputs, including `checks` derivations and NixOS toplevels; it does not document `darwinConfigurations` as a built-in checked output. Thus a generic flake check should not be used as the sole evidence that a Darwin configuration evaluates/builds. Explicitly target the Darwin system or expose it through a deliberate check. [Nix manual](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake-check.html)
- Ryan's workflow runs expression tests on Ubuntu and explicitly compares the resulting JSON to `true`, because a successful `nix eval` process alone does not mean the test result is true. The additional runtime job is a Linux firewall VM test. This is useful testing discipline, but it must not be reported as macOS GUI/launchd activation coverage. [Workflow](https://github.com/ryan4yin/nix-config/blob/b334336cd9e4970c8e35a6cb154a57f4051ba77a/.github/workflows/flake_evaltests.yml)
- Dustin's scheduled update workflow opens lock-update PRs, but its prerequisite build is a starter template on `x86_64-linux`; the shown build workflow also targets that template/platform. These files demonstrate update automation, not validation of the personal Darwin host or proof that the eventual updated lock was built on Darwin. [Update workflow](https://github.com/dustinlyons/nixos-config/blob/d8f6dd8063bf535613e55ca9a4d57827c9103b0e/.github/workflows/update-flake-lock.yml) · [Build workflow](https://github.com/dustinlyons/nixos-config/blob/d8f6dd8063bf535613e55ca9a4d57827c9103b0e/.github/workflows/build.yml)
- Local system configuration already provides generation cleanup through `programs.nh.clean` with `--keep 5 --keep-since 7d`; local HM wiring backs up conflicting unmanaged files. These are useful operational facilities, but retention/backups should not be confused with testing or with backing up all application data. [System](file:///Users/martin/nix/darwin/system/configuration.nix) · [HM bridge](file:///Users/martin/nix/darwin/system/home-manager.nix)

### Inferences

Recommended sequence (proposals only; none executed here):

1. **Document the current contract first.** Add a short maintenance section: one Apple Silicon host `mb-pro`, one user, unstable main input family, stable oxker exception, stateVersion rationale, and app ownership/update boundaries. Retain the current flake and explicit imports.
2. **Make the maintenance path repeatable.** Document or wrap: review input/lock changes and relevant release notes; format/review the configuration diff; explicitly build `nix build .#darwinConfigurations.mb-pro.system`; then activate using `sudo darwin-rebuild switch --flake .#mb-pro`; verify the shell, GUI app launch, and launchd-dependent desktop features actually used. These commands are proposed based on the observed public workflow; no commands were run during this research.
3. **Explain recovery and retention.** Record how the owner restores a previously known-good configuration/lock and rebuilds it, and how that interacts with retained generations. Document that Homebrew changes and app data are a separate recovery boundary. Keep the existing retention policy unless user needs dictate another one.
4. **Track exceptions with retirement conditions.** The oxker fallback already explains why it exists. Add the condition for removing it and periodically reconsider the fallback during relevant updates. The package list also contains a localized Prism Launcher workaround linked to an upstream PR—continue that narrowly scoped pattern rather than broad global overrides. [Package workaround](file:///Users/martin/nix/darwin/home/packages.nix)
5. **Extract only where navigation or reuse improves.** The README already proposes a development-tools module; that is a reasonable small extraction if the package list is becoming difficult to navigate. Larger program blocks can similarly move into named files while preserving the explicit list. Do not add a second abstraction layer solely to resemble a fleet repository. [Local TODO](file:///Users/martin/nix/README.md) · [Program aggregation](file:///Users/martin/nix/darwin/home/programs/default.nix)
6. **Grow host/user structure when it is needed.** For a second Mac, add a narrow host module and share the existing system/home layers; for Linux, separate genuinely portable home modules from Darwin services/apps. Reuse the existing typed feature-module approach where coupled behavior needs a single switch.
7. **Add automation last, with honest coverage.** A small explicit Darwin evaluation/build target is more valuable than a sophisticated framework with unclear coverage. CI can later run formatting/static checks and suitable platform builds. Reserve macOS activation/GUI checks for a real compatible host; do not label Linux evaluation as macOS runtime testing.

### Gaps

- Other workstreams own full bug detection, lock compatibility checks, build/evaluation results, and activation correctness. These notes intentionally do not supply pass/fail claims in those areas.
- Whether CI is worth its maintenance cost depends on edit frequency, available macOS runners, and the owner's tolerance for manual verification. The comparative evidence supports a reproducible local workflow first, not a mandatory CI platform or framework.
